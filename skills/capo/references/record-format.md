# 运行记录格式

可使用 Markdown 或结构化数据。运行记录的字段用于关联观察和决策，实际状态以宿主、产物和验证结果为依据。按时间保留历史、来源与结果，未知字段显式标为 `unknown`。

| 记录 | 最少内容 |
| --- | --- |
| 运行和需求 | `run_id`、目标、原始要求、历次 `requirement_version`、变更来源、验收项 ID、验证方法、任务依赖和当前交付物 |
| 上下文 | `context_revision`、对应需求版本、快照路径或摘要、来源、受影响任务与失效条件 |
| 任务和分派 | 持久 `task_id`、稳定操作对象、依赖、`assignment_revision`、需求和上下文版本、Worker ID、实际工作目录、可写范围、交接证据、交付物及状态 |
| 派发尝试 | 尝试 ID、时间、任务与分派、宿主及入口、是否可能启动轮次、模型 `role`、`requested_model`、`effective_model`、`model_source`、请求及实际推理档位、并发和研判预留、返回及后续核查 |
| 额度 | 用户授权及来源、用户并发限制（未设置则注明）、宿主容量与计数口径及来源（未知则注明）、全树占用和预留、研判额度、已用、预留和待确认消耗、停止控制例外 |
| 暂停控制 | `pause_id`、`scope`、`control_revision`、用户原话和时间、停止请求与实际观察、解除记录 |

## 消息和 Worker 回报

- 为每次版本投递记录 `message_id`、目标 Worker、`task_id`、`assignment_revision`、`requirement_version` 和 `context_revision`。工具确认发送才记录 `sent`；Worker 明确确认理解对应版本，或提交能证明已处理该版本的回报，才记录 `ack`。分别记录时间和依据。工具返回未知时保留未决投递状态。
- Worker 回报携带任务和分派及需求、上下文版本，附实际改动、验证命令及结果、证据路径、前后变化、未验证项及卡点。`progress` 表示仍在执行，`ready` 表示提交验收，`blocked` 表示受具体条件阻塞，`failed` 表示已尝试但未完成。无需改动时用 `ready` 并附可验证证据。
- `dropped` 由 Router 记录。取消任务时标记任务，替换时标记旧分派并保留继续执行的任务。旧分派迟到回报留作历史。`sent`、`ack`、`ready` 均不推进验收状态，也不能证明实际停止或写域释放。

## 验收与证据沿用

每条验收记录含 `evidence_id`、`task_id`、`requirement_version`、`context_revision`、`assignment_revision`、`criterion_id`、`artifact_digest`、`result`，以及验证者、证据位置、方法、实际结果。`result` 只用 `passed`、`failed`、`unverified`。验收依据最终产物内容计算的摘要，例如指定文件集的 SHA-256，或宿主提供的不可变工件版本。记录摘要覆盖范围；不能确定产物身份时保持 `unverified`。集成影响到产物摘要或验证输入时对受影响项重验。

需求、上下文或分派变化后逐项检查证据适用性。只有 Router 核实验收项、输入、验证方式和产物相关行为均未受影响，且新旧产物摘要相同，才可生成绑定当前各版本的沿用记录，注明 `carried_from` 的旧证据 ID、未受影响的理由及摘要核对结果。旧记录保留原绑定；外部条件变化、产物摘要变化或适用性未知时，当前项标为 `unverified`，重新验证。旧分派回报不得直接登记为当前验收。

## 记录存储受限

记录位置不可写时使用会话内记录，注明未持久化及跨回合恢复限制。先落实暂停和停止控制，存储故障不得阻塞这类操作。恢复写入后补记原顺序、来源和仍未核实事项。重新进入会话时若无法重建暂停、占槽或写域事实，保持相关范围停止推进，先核查宿主状态、历史和产物。
